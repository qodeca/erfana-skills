# Known caveats (v4.0.0+)

Accepted risks introduced by the v4.0.0 scope widening, the v4.1.0 hooks migration, subsequent feature releases, and operational incidents (v4.2.0 rc.1 soak cut short, the 2026-05-15 `6fa70e5` commit-verification incident, the 2026-05-17 v4.2.8 → v4.2.10 same-day release chain, the v4.2.13 / v4.2.19 managing-issues hardening releases, and the v4.2.20 cross-platform-hooks Windows-coverage gap plus its gate-portability fix). Beyond the flat bullet list below, the file carries one `##` section per release that added caveats – today v6.2.0 (grill-me), v6.4.0 (managing-skills), v5.0.0 (managing-specs), v6.5.0 (managing-issues Implement hardening) and v6.6.0 (grill-me proportional depth). Section order is the order they were written, not chronological; **the last section in the file is the newest and is the only place that carries the running no-staged-rollout tally**. Counts stated inside older entries ("six overrides", "the 7th consecutive no-soak release") are historical – true when written, not maintained since. None of this blocks releases, but every maintainer should know about it.

## v6.2.0 grill-me — sentinel backstop is advisory, not a lock (accepted risk)

The v6.2.0 grill-me rewrite adds a skill-scoped `grill-guard` Stop hook (declared in `skills/grill-me/SKILL.md` frontmatter) that blocks a stop attempt whose last assistant message still ends with the open marker. Three accepted limitations, all inherent to current Stop-hook semantics: (1) the block fires **once per stop attempt** – `stop_hook_active: true` short-circuits the retry, so the hook is one forced continuation, not a gate; the protocol's real strength is the in-skill coverage-map exit gate. (2) The backstop is **contingent on marker emission** – a model that drops the marker early exits silently; the rationalization table addresses this in prose, nothing enforces it. (3) After **context compaction** the skill text may leave context, marker emission stops, and the backstop silently ends; post-compact re-injection via the post-compact-reminder hook is a tracked follow-up, not shipped. Additionally, two platform behaviours were undocumented at ship time and verified only by dogfood: `${CLAUDE_PLUGIN_ROOT}` substitution inside skill-frontmatter hook commands, and `last_assistant_message` content when a turn ends at an `AskUserQuestion` call (the hook fails open on empty input by design). The `.ps1` sibling was behaviourally verified via a local pwsh replay of all 5 fixtures (plus the 10 verify-completion fixtures as regression) on 2026-07-22; Linux CI exercises only the `.sh`, so future `.ps1` edits need a manual pwsh replay – same drift-watch pattern as the v4.2.20 hooks caveat. One residual protocol limitation from the post-fix eval runs: the "ladder at least one rung" floor bounds breadth, not depth – a completion-biased interviewer can satisfy `[x]` on every dimension with single-rung follow-ups while a fact sits one probe deeper. A hard depth quota was deliberately rejected (Goodharting risk); if real sessions under-probe, the candidate follow-up is a depth heuristic ("ladder until the answer stops adding new nouns") rather than a numeric floor. **Superseded in part by v7.1.0:** the guard no longer lives at the path named above and is no longer declared in SKILL.md frontmatter - it moved to `hooks/` and `hooks/hooks.json`, and now evaluates every stop rather than only stops inside its skill. See the v7.1.0 section at the end of this file.

## v6.5.0 (PR #24) managing-issues – the hardened Implement operation ships unexercised (accepted risk)

**Superseded by the v6.7.0 autonomous rework** (see the v6.7.0 entry below): the interactive design described here no longer ships, so this section's present-tense "is now interactive-only" claims read as historical.

The Implement hardening on `feature/managing-issues-implement-hardening` turns eight prose checkpoints (nine prompt sites) into blocking `AskUserQuestion` calls, adds three sub-gates (`QG-4a` and `QG-11a`, lens reviews the **user** runs; `QG-4b`, architecture acceptance on every pass), risk-scaled test enforcement at QG-5, and run-state persistence in one issue comment with an authenticated resume path. Phase count stays 13; gate count becomes 13 phase gates plus 3 sub-gates. The operation is now interactive-only and refuses a detected headless run. Seven accepted risks, highest severity first:

1. **The operation has never been run end to end, at either tier.** No T1 run and no T2 run has been executed against a real issue since the change – not one pass through the 13 phases, the sub-gates, the resume path, or the test-enforcement matrix. Everything asserted about the flow is read from the prose, not observed. **This explicitly retires the "manual dogfood is the regression backstop" claim** made in the v4.2.13 and v4.2.19 bullets above: there is no automated test suite for `managing-issues`, and after this change the manual backstop is itself unexercised. The standing safety net is the static gate suite plus `claude plugin validate`, neither of which executes a phase. A first live run at each tier is the highest-value follow-up; until it happens, treat a first-report regression as most likely originating in the new blocking checkpoints, the QG-0 test-command resolution, or the resume path.
2. **No staged rollout, again.** This change alters runtime behaviour for every auto-update user of the Implement operation (more blocking stops, two turn-ending checkpoints, stricter test enforcement, a new issue write) and squarely meets the CLAUDE.md staged-rollout triggers; no `rc.N` tag is planned. Counting the overrides that have their own entry in this file – v4.0.0, v4.1.0, v4.2.0, the v4.2.8 → v4.2.10 chain, v4.2.13, v4.2.19, v5.0.0, v6.4.0 – this is **at least the ninth consecutive no-soak release**. That figure is the file's running tally and lives here only; older sections keep the number that was current when they were written.
3. **A repo collaborator can edit the persisted run-state comment in place.** The authorship filter is applied in the fetch query, so a comment from a member of the public is never ingested; it cannot, however, detect an in-place edit of the authenticated user's own comment. A collaborator with write access can therefore land up to 80 shape-validated `key: value` lines (400 chars each) in orchestrator context. The mitigations – shape validation, known-keys-only parsing, and re-deriving every gate-deciding field (`review_level`, tier, branch, QG-0 / QG-7 / QG-9 outcomes) rather than reading it back – make that content **harmless, not prevented**; the text still enters context. The bound is meaningful: this requires write access to the repository, which puts it outside drive-by reach. Detail and the full accepted-exposure statement: [`../skills/managing-issues/reference/run-state-resume.md`](../skills/managing-issues/reference/run-state-resume.md).
4. **On a private repo the run-state comment is written with no prompt and is never removed.** The consent `AskUserQuestion` fires only when the repo is public (the reasoning: on a private repo the audience is already the repo's collaborators, and the run should not spend a blocking stop on it). The user-facing consequence: **a user who wants no issue write at all on a private repo has no prompt at which to decline.** The write is announced in one line after the fact, the comment is edited in place rather than duplicated, and the run never deletes it – it stays as the audit trail. Removing it is a manual action.
5. **Every stop count in the skill's docs is hand-traced, not measured.** The "four unconditional stops", "14 at the default review level", "17 on the common default" figures were counted by reading the phase files; an earlier pass under-counted every figure by one.
6. **A resume no longer requires a clean working tree.** Pre-flight Step 3 records the dirty paths and reports them instead of failing (an interrupted implementation has uncommitted work by construction), and **nothing attests those paths came from this run** – no diff hash is persisted, and edits made between interruption and resume are indistinguishable from the run's own. The Phase 12 pre-commit re-review, which runs with no baseline on any resume and therefore re-reviews the whole working-tree change set, is the compensating control.
7. **A standard run now writes and commits a design doc into the consumer's repository.** When no spec is linked and QG-4a is in scope, Phase 4 writes `docs/design/design-issue-<N>.md` – or `<repo-root>/design-issue-<N>.md` when the repo has no `docs/` tree – and Phase 12 commits it with the change. The path is surfaced at QG-4a Step 1 and the file is user-approved at QG-4 / QG-4b, but the net effect is a new, unrequested file class appearing in users' repositories via an auto-updating plugin.

## v6.6.0 grill-me — depth is model judgement, and the no-soak streak reaches ten (accepted risk)

v6.6.0 makes `grill-me` size its own interview: three depths (`short` / `standard` / `full`) selected by the model from four observable plan properties, batched skips that proceed without per-area approval, and a depth-relative question floor replacing the flat "fewer than 10". Four accepted risks:

1. **Nothing deterministic stops the model from always choosing `short`.** Depth selection is model judgement each run. The sole guardrail is the mandatory sizing statement – the opening message must state the selected depth, the four properties behind it, and the batched skip list – which catches a bad size only if the user reads it. The obvious hardening (named conditions that force `full` regardless of apparent size: money, data loss, published interfaces) was **offered during requirements gathering and explicitly declined by the maintainer** in favour of the lighter mechanism. This is the exact failure mode the skill exists to prevent, now re-admitted under a visibility control rather than a structural one. If real sessions under-question, the ready-made follow-up is the hard-rule list.
2. **Batched skips weakened exit-gate condition 1.** It moved from "`[w]` with the user's explicit confirmation" to "`[w]` with its reason stated" – the two could not coexist once skips stopped stopping for approval. The gate still requires a fully `[x]`/`[w]` map, the prediction test, the meta check, a standalone read-back message, and user confirmation, at every depth. Net effect: a skip is now visible-and-reasoned rather than user-acknowledged, so an unread sizing statement closes areas the user never actually considered.
3. **No staged rollout, again.** This alters runtime behaviour for every auto-update user of `grill-me` (materially fewer questions on plans the model sizes down) and adds two `when_to_use` trigger phrases (`"quick grill"`, `"grill me lightly"`) – squarely two CLAUDE.md staged-rollout triggers, skill-behaviour change and trigger-phrase change. Shipped as a routine release with no `rc.N` soak by explicit maintainer decision. This is the **tenth consecutive no-soak release**, extending the tally in the PR #24 entry above.
4. **The new behaviour ships unexercised.** No interview has been run end to end under the depth model – not a `short` pass, not an upward re-size, not a batched-skip statement. Gate coverage is static (frontmatter, links, sentinel symmetry, counts); no gate executes an interview. The `grill-guard` Stop hook and the `<!-- erfana:grill-open -->` sentinel are untouched and keep their v6.2.0 caveats above verbatim.

## v6.6.1 skill registry + Gate 18 — a generated doc with three unguarded edges (accepted risk)

`docs/skill-registry.md` is generated from git history (`scripts/gen-skill-registry.sh`) and policed by Gate 18. The gate deliberately warns rather than blocks on stale dates – the rationale is in [`gates/18-skill-registry.md`](gates/18-skill-registry.md) and is not repeated here. Four accepted risks:

1. **A stale row's commit subject is verified by nothing.** Check 3 compares the subject only when the date matches, because a matching date is what pins the exact commit. A row that is behind git may therefore carry any subject at all, and a date hand-edited *backwards* is indistinguishable from ordinary lag – both warn. The column most likely to be read as authoritative is the one with the weakest guarantee when the file is lagging, which is its normal state between releases.
2. **The rendering rule is mirrored between two scripts, not shared.** Subject truncation (72 chars) and pipe escaping are implemented identically in `gen-skill-registry.sh` and `gate-18-skill-registry.sh`; nothing enforces that they stay identical. Editing one without the other makes the gate reject rows the generator legitimately emits. Both files carry a warning comment; that is the whole control.
3. **Dates are path-scoped, so work that plainly affects a skill can leave its row untouched.** Only commits touching `skills/<name>/` move a date. `managing-articles` is the standing example – its five `article-*` agents live at plugin root, so agent work never dates its row, and the registry will read "untouched since v6.0.0" while the skill's behaviour changes.
4. **No staged-rollout obligation, and the no-soak tally is unchanged.** This is maintainer-facing infrastructure: a gate, a generator, and documentation. It ships no skill-behaviour or trigger-phrase change and nothing reaches an auto-update user's runtime, so none of the CLAUDE.md staged-rollout triggers apply. The tally therefore **stands at ten**, as recorded in the v6.6.0 entry above; this entry does not extend it.

## v6.7.0 managing-issues – autonomous Implement operation (accepted risk)

v6.7.0 reworks the Implement operation from interactive to **autonomous**: it designs, builds, reviews, and fixes without blocking on intermediate approvals, resolving every architecture/technical decision by best practice plus conditional research plus judgment. The former user-run `/erfana:lens-review` steps are gone – reviews are embedded (QG-4a, QG-8, QG-11a fan out the operation's own reviewer agents), CRITICAL/HIGH findings are auto-fixed and re-verified inline, and MEDIUM/LOW go to the `mi-solution-designer` JUDGE mode (fix / accept-as-tech-debt / not-worth-it) bounded by a 3-round `embedded_loop_iter` cap. Human interaction is limited to requirements clarification (Phase 2), UAT acceptance (QG-11), the QG-12 git-action confirmation, and the QG-0 public-repo run-state consent; the operation still refuses a detected headless run. Five accepted risks, highest severity first:

1. **The autonomous rework ships unexercised.** No end-to-end run at either tier has been executed since the change – the static gate suite plus `claude plugin validate` execute no phase. Same standing pattern as the v6.5.0 and prior entries: there is no automated test suite for `managing-issues`, and the first live run at each tier is the highest-value follow-up.
2. **The judge-mode agent edit shipped uncommitted in v6.7.0.** The `mi-solution-designer` JUDGE mode – the MEDIUM/LOW finding triage the operation now depends on – was left out of the v6.7.0 release commit and reached `main` describing a mode the agent file did not contain. It is being corrected on `develop` and lands with the next release. Until then, a v6.7.0 run's judge step falls back to the agent's planning contract.
3. **No staged rollout, again.** v6.7.0 materially changes Implement runtime behaviour for every auto-update user and met the staged-rollout triggers; it shipped as a routine release with no `rc.N` soak by explicit maintainer decision. This is the **eleventh consecutive no-soak release**, extending the tally the v6.6.0 entry called the tenth.
4. **Autonomous fixes reach UAT before any human review.** CRITICAL/HIGH findings are auto-fixed inline and MEDIUM/LOW are judged without a human in the loop; the first a human sees of the technical work is the finished result at UAT. A wrong auto-fix or an over-eager "not-worth-it" verdict is only caught at UAT.
5. **The `embedded_loop_iter` cap is session-local.** It resets to 0 on resume, so a resumed run can add up to another 3 fix rounds per gate beyond what already ran. This is deliberate: persisting the counter in the untrusted run-state comment would let a forged block cut the loop short.

## v7.1.0 second host – a supported target nobody has run a skill on (accepted risk)

v7.1.0 makes Qwen Code a supported host. One package, converted at install time; no second manifest and no build step. Nine accepted risks, in rough order of how much they should worry a maintainer.

1. **No erfana skill has run end to end inside a Qwen session.** Everything verified on this branch verifies the loader and the wiring: the plugin converts, the counts survive, `hooks.json` arrives byte-identical, the sentinels survive, the extension registers. `scripts/qwen-smoke.sh` deliberately runs with no model credentials, so it never enters Qwen's hook runner and never executes a skill. A green smoke run must not be reported as "erfana works on Qwen" – it proves the loader, not the executor. The rc soak on both hosts is what is meant to close this.
2. **The guards now evaluate every stop, and the forced-continuation budget is shared.** `grill-guard` and `ms-grill-guard` moved out of SKILL.md `hooks:` frontmatter into `hooks/hooks.json`, because Qwen never extracted that frontmatter and a skill-scoped guard was dead on one of the two hosts. They previously fired only while their skill was loaded; they now evaluate every stop of every erfana session, scoped by the open-marker sentinel alone. `stop_hook_active` is one field in one payload and all three Stop hooks short-circuit on it, so a guard block consumes the single continuation `verify-completion` would otherwise get. That is a net reduction in `verify-completion`'s effective coverage, accepted deliberately. The v6.4.0 entry above describes this risk for managing-skills sessions only; it now applies everywhere.
3. **A false block now lands without the protocol in context.** The block reason names an interview the model may never have loaded, so both reasons were rewritten to be self-contained. Four false-block shapes found in review are fixed with fixtures – a fence indented under a list item, a `~~~` fence, a backticked prose mention, and the marker mid-prose – but the scrub is a heuristic over markdown, not a parser. The odd-fence fallback still blocks by design: an unclosed fence earlier in the message falls back to the raw body. The sentinel appears in thirteen tracked non-test files including `CLAUDE.md` and this one, so maintainer sessions are the likeliest place to meet a false block.
4. **Both security hooks fail open without `jq`, and the launcher only says so.** `bash-safety` and `secret-detector` parse their payload through `jq ... 2>/dev/null || true` and reach their allow branch on an empty value. Stock macOS ships no `jq`. `dispatch.sh` now probes for it and emits a diagnostic, but the diagnostic goes to stderr with exit 0, which Claude Code is documented to surface only for non-zero, non-2 exits – so on the very host the probe was written for the skip is probably silent. The probe is per-hook: `post-compact-reminder` needs no `jq` and is exempt, with a fixture proving it.
5. **The watchdog fails open, and its no-watchdog direction is unbounded.** A killed hook exits 143 - the watchdog sends SIGTERM, so 128+15; 142 is what Qwen's own timeout produces - or dies by signal, never 2, so neither host reads it as a block: a killed `secret-detector` lets the write through. Same direction as before, but with the `hooks.json` `timeout` key gone this is now the only bound. Two narrower holes remain: the stdin-buffering phase (`cat > "$PAYLOAD"`) runs before the watchdog exists, so a host that holds the pipe open stalls up to its own default (600 s on Claude Code) rather than 5 s; and an unwritable `TMPDIR` or full disk makes `mktemp` fail, taking the safety net offline with a bare `mktemp:` message that names neither erfana nor the hook. Both were judged not worth more launcher machinery.
6. **The buffered payload reaches disk.** Under the old `exec` the payload existed only in a pipe. It is now written to a `mktemp` file at mode 0600 and removed by an EXIT trap – which runs on SIGTERM but not on SIGKILL or a hard crash. For `secret-detector` the payload *is* the candidate secret, so the hook whose job is to stop a key reaching disk writes that key to `$TMPDIR` on every Write and Edit.
7. **The launcher is no longer signal-transparent.** With the child in its own process group, a SIGTERM to the dispatcher orphans the hook rather than killing it, a group-directed SIGTERM kills the watchdog and leaves the hook running unbounded, and the child ignores a direct SIGINT (bash sets async children to ignore it). For erfana's read-only hooks the blast radius is a stray process, but the file's own "the dispatcher is transparent" claim is true of stdin, stdout, stderr and the exit code, not of signals or process lifetime.
8. **The alias map is a transcription of one Qwen version.** `scripts/_lib/host_matrix.py` holds tool aliases and the agent-frontmatter allowlist read out of Qwen 0.22.3's bundle by hand. The smoke test checksums the chunk they came from and Gate 15 forces the CI pin to agree, so the pin and the transcription are always equal – which means the version check can never fire from CI alone. The weekly `qwen-canary` workflow against `@latest` is the only thing that ever moves the pin; if it is disabled, the transcription rots silently. A future Qwen that *does* support extension `hooks:` frontmatter would double-register the guards.
9. **CI tests the working tree, not the shipped artifact,** and `model: opus` on 67 agents remains unresolved. A silent fallback to a Qwen-side default is indistinguishable from resolution, so no check on this branch can observe it. It stays open until someone finds a way to read back the resolved model inside a Qwen session.

Two smaller behaviour changes, recorded so they are not mistaken for bugs: `commands/project-status.md` and `commands/session-status.md` gained a `description`, so `/help` and the command picker now show that text instead of the file's first line (both keep `disable-model-invocation: true`, so neither becomes model-invocable); and the three argument-taking commands gained a resolution step above their existing contract, which a model may narrate before emitting its single required line.

**Staged rollout.** This release changes hook configuration, moves two hooks, and rewrites 34 of the 87 agent bodies – squarely inside the staged-rollout trigger list. The rc soak is therefore **not** waived here, breaking the streak the v7.0.0 entry above counted at thirteen. Both CLIs are installed on the maintainer's machine, so the soak costs two commands.
